Experiment Coming

Large or small model: what does each cost?

For one simple task, how much does a large general model add over a small one trained for the job, and how much more energy does it use?

This experiment has not run yet

This page sets out how we will run it. There are no results below, only empty cells. When we have run it, we will publish the numbers, the data and the code here, with a short write-up.

Why this experiment

A common assumption is that a bigger model is always better. PetaBencana argues the opposite for its own work: that smaller, well-curated datasets can be more accurate than large models, and use far less energy. This experiment puts a version of that claim to a simple, open test, and makes the frugal lens something you can measure.

The task

Sort short posts written like social media updates into two groups: 'reports a flood happening now' or 'does not'. It is the same task as step one of the flood report walk-through, at a larger scale. We chose a text task because it is cheap to run, needs no images and needs no data from any initiative.

The data

About 600 example posts in English that we will write ourselves: 400 to train the small model and 200 held back to test both models. Half describe a flood happening now; half do not, including hard cases such as 'a flood of messages', memories of past floods and warnings about tomorrow's rain. No real posts and no PetaBencana data are used. We will publish the full set.

The two models

ArmModelHow it runs
LargeAn open-weights general language model with about seven to eight billion parameters. We will record the exact model and version.Asked to sort each post with one fixed instruction and no training. Runs on one computer we can measure.
SmallA simple word-counting classifier (TF-IDF features with logistic regression), trained on the 400 training posts.Trains and runs on an ordinary laptop processor.
Optional middleA small sentence model of about 100 million parameters with a simple classifier on top.Laptop processor. Added only if the first two are far apart.

We leave out large models offered only as paid online services. Their energy use cannot be measured from our side: our tools would only see our own computer sending a request. If the write-up mentions them, it will quote published estimates and say clearly who made them.

How we will measure energy

We will use CodeCarbon, an open-source tool that estimates the energy a computer uses while running a piece of code (processor, graphics card and memory) and converts it into an estimate of emissions using the carbon intensity of a country's electricity grid. We will run it offline with one fixed country, so the results can be repeated, and report energy in kilowatt-hours as well as emissions, so you can apply your own grid.

  1. Record the computer used: processor, graphics card, memory, operating system and software versions.
  2. Measure the computer at rest for five minutes, to report alongside.
  3. Small model: measure training once, and sorting the 200 test posts separately.
  4. Large model: measure sorting the 200 test posts. Downloading the model is not counted, and we will say so.
  5. Repeat each sorting run three times and report the middle value.

What it will not show

  • One task, one computer and example data. Other tasks and other machines will give other numbers.
  • Estimates, not readings from a meter. CodeCarbon does not count storage, networks or cooling.
  • Large models can do many more things than this task. The question is whether this task needs one.
